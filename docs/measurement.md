# 测试信号与测量边界

## 两种信号播放路径

- **PC 信号源**：浏览器运行在实际输出 HDMI 的电脑桌面上；全屏播放器通过 `requestVideoFrameCallback` 和 `getVideoPlaybackQuality` 记录浏览器观察到的播放状态。
- **外部设备（PS5 等）**：把下载的 CFR 视频传到实际 HDMI 信号源设备，使用兼容的播放器全屏、1×速度播放。预览电脑上的网页不是真正的外部参考。部分 PS5 应用/设备不能播放此文件或帧率，需先确认支持，否则改用兼容 HDMI 播放器或 PC。

外部模式没有网页信号播放，完成状态是**用户确认已拍摄**：`source=external`、`recordingConfirmed=true`，`diagnostics.complete=false` 表示浏览器没有观察播放，不等于用户确认的录像中断。外部输出稳定性未验证，掉帧/重复帧诊断不可用；不会生成伪装成实测的零掉帧数据。

HDMI 参考画面是采集卡 HDMI OUT 的直通画面；USB 采集预览是 Veyra/OBS 在电脑上显示的采集画面。两区同框、同垂直高度。第二轮仅推荐，必须实际交换 PBP 输入位置或显示器位置，网页元素移动不算交换。

## 三种时间尺度

- 源视频 FPS：编号/内容的步进周期，60FPS 一帧约 16.67ms。
- 显示器 Hz：显示刷新周期，由用户核对系统设置，不由本站实测。
- 手机拍摄 FPS：相机采样周期，120FPS 约 8.33ms，240FPS 约 4.17ms。

标准配置要求 Hz ≥ 源 FPS，且 Hz 是源 FPS 的整数倍。默认 60Hz / 60FPS / 手机 120FPS。60Hz 禁用 120FPS 源，手机 120/240FPS 照常支持。从 120Hz 降至 60Hz 时，120FPS 源自动回退为 60FPS；144Hz 对当前 30/60/120FPS 素材不满足均匀保持条件，会阻止启动，提示先在系统设置中选择兼容刷新率。59.94Hz 与整数 60FPS 素材也不严格匹配。

这只验证**填写的配置**是否匹配，不代表物理逐帧输出得到验证。rAF 节奏是浏览器回调估计；视频帧回调提交到合成器，也不是 HDMI 或面板扫描观测。

## V2 素材和机器码

保留固定 LCG 种子 `0x56455952`、原有 30/60/120FPS、每帧编号、全部事件边界和总帧数。每种帧率提供 20/50/100 事件，前一秒为 EVENT 000，随后每约 0.4–0.8 秒切换一次局部方块，末事件保留完整持续时间。视频不循环。

V2 将数字字号由 102 放大到 250，并把 `FRAME ID` 标签独立放置；保留 EVENT ID、约 500×250 像素的亮度区域与四角定位标记。小型机器码在同一视频帧内由 FFmpeg 的 `n` 驱动，没有网页定时器或独立时钟。

从左到右的 32 格：

| 位 | 内容 |
| --- | --- |
| 0–3 | 固定同步 `1010` |
| 4–19 | 16 位源帧编号，最高位在左，范围 0–65535 |
| 20–27 | CRC-8/SMBUS：poly `0x07`、init `0x00`、不反射、xorout `0x00`；按帧编号两个大端字节计算 |
| 28–31 | 固定结束 `0101` |

原始素材 1280×720：码带左上 `(65,638)`，格边长 26 像素，中心间距 34 像素。先定位手机录像中各画面区域，校正透视和缩放，再读取格中心；白为 1，黑为 0。源码中 `scripts/signal_codec.py` 提供 `crc8`、`decode_frame_code(bits)`；无效码返回 `None`，不能把源帧 0 当成无效值。

CRC 用于检测读码错误，**不能纠错，也不证明帧实际输出或硬件延迟**。曝光/滚动快门可能使同一行混合两个源帧；CRC 不通过时剔除该次读码或回退到大号数字与 EVENT ID。码带和大号数字处于不同扫描行：即使 CRC 正确，也可能因面板扫描/滚动快门呈现相邻源帧。比较两路同垂直位置的同类标记，并分开记录数字/码带结果。少数多位错误可能通过 8 位校验，不应仅凭 CRC 提升整段录像的可信度。数字与小型码带逐帧变化，光敏者请勿观看。

## 生成和验证

生成器先写临时目录，全部新增视频通过逐帧验证后才发布版本化文件名 `signal-v2-FPS-EVENTS.mp4` 和清单，避免混用 V1 缓存。首次迁移 V2 必须生成三种 FPS；后续可 `--fps 60` 单独重生成。短版从完整序列无重编码裁剪。编码使用 H.264 yuv420p、B 帧关闭、快速起播；字节哈希可能随 FFmpeg 版本变化，事件时序仍确定。

`verify-signals.py` 解码**每份**素材的全部帧，校验：逐帧 PTS / 平均和标称 FPS / 总帧数 / SHA-256 / 数字区域唯一性 / 每帧方块亮度 / 32 格同步、实际帧编号及 CRC。CRC 标准算法另用已知 `123456789 → F4` 检查向量及全部单比特破坏验证。构建还核对 V2 清单与 9 份素材摘要。

## 浏览器诊断和结论局限

- 小号回调编号只是低频快照，拍摄/分析读取源视频中的大号数字和机器码。
- 浏览器掉帧数是浏览器报告值。回调媒体时间间隙、重复回调时间戳不等于物理 HDMI 掉帧或重复帧。
- API 缺失、缓冲、退出全屏或回调节奏不匹配会记录为限制；页面进入后台、播放中断、改速或手动停止标为未完成。
- 高拍摄 FPS 降低采样间隔，但源 FPS、显示扫描、滚动快门和曝光仍限制准确性。部分 480/960FPS 手机模式只能拍短片段。
- 慢动作导出可能降为 30FPS 或重写减速时间戳。保留真实原始文件/ZIP，不能从“播放多慢”反推真实采样率。
- 0 源帧差不是 0ms；结果是本显示环境中两条路径的**可见延迟差**，不一定是采集芯片内部延迟。
- 浏览器无法可靠验证真实 HDMI 时序、面板扫描、物理重复帧或外部播放器稳定性，本站不自动分析录像，也不生成未测量的延迟统计。
